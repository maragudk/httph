# Diary: CSP nonce support in `ContentSecurityPolicy` (issue #28)

Let the `ContentSecurityPolicy` middleware generate a per-request CSP nonce, append it to `script-src` and/or `style-src`, and expose it to handlers via `GetNonceFromContext`. Motivated by Datastar 1.0.3's CSP mode, which needs a nonce in `script-src` to drop `'unsafe-eval'`. Downstream: maragudk/glue#203, maragudk/app#64.

## Step 1: Refine the design

**Author:** main

### Prompt Context

**Verbatim prompt:** "See issue 28"
**Interpretation:** Read issue #28 and take it from proposal to shipped feature.
**Inferred intent:** Unblock Datastar CSP mode in glue and app by adding nonce support to httph with the smallest sensible API.

### What I did

Read issue #28, glue#203 and app#64, and the current `ContentSecurityPolicy` in `/httph.go`. Brainstormed the design with Markus one question at a time. Decisions:

- Option A only (httph owns the nonce). No `ContentSecurityPolicyWithRequest`; option B is additive later if a real per-request-directive need appears.
- Per-directive bools on `ContentSecurityPolicyOptions`: `ScriptSrcNonce` and `StyleSrcNonce`, both off by default. Not always-on, because a nonce makes browsers ignore `'unsafe-inline'` in the same directive, which would silently break apps that set `StyleSrc: "'self' 'unsafe-inline'"`.
- `GetNonceFromContext(ctx) string`, returning `""` when absent. Named to match glue's `GetUserIDFromContext`/`GetPermissionsFromContext`. Not a pointer: `""` is an unambiguous zero value here, unlike a user ID.
- Always generate a fresh nonce; overwrite any nonce from an outer middleware.
- Nonce from `crypto/rand.Text()` (Go 1.24+), so `go.mod` bumps from 1.19 to 1.24. There is no `crypto/rand/v2`; checked.

### Why

The only concrete need is a nonce. Doing the security-sensitive part once in httph beats every app reimplementing generation, formatting, and context storage.

### What worked

The issue was already a well-argued proposal, so the brainstorm was four questions.

### What didn't work

Nothing failed. `gh issue view 28` printed nothing with plain output; `--json` worked.

### What I learned

`rand.Text()` exists since Go 1.24 and is exactly this use case: at least 128 bits, base32, never fails.

### What was tricky

Deciding against always-on: the `'unsafe-inline'` interaction is the argument, and it is also the argument for per-directive control.

### What warrants review

The design itself, before code: see Step 2 for implementation.

### Future work

glue#203 (thread nonce into `PageProps`, fix 404s outside the CSP group) and app#64 follow-up once this is tagged.

## Step 2: Implement nonce support

**Author:** nonce-builder

### Prompt Context

**Verbatim prompt:** "You are building CSP nonce support for the `ContentSecurityPolicy` middleware in `maragu.dev/httph`, resolving GitHub issue maragudk/httph#28. [...] Add two fields to `ContentSecurityPolicyOptions`, both default `false` [...] Add `GetNonceFromContext` [...] generate ONE nonce with `crypto/rand.Text()` [...] Bump `go.mod` from `go 1.19` to `go 1.24` [...] Tests, added to `TestContentSecurityPolicy` in `httph_test.go` in the existing style."
**Interpretation:** Build exactly the design from Step 1, with tests, in the worktree, without widening the API.
**Inferred intent:** Ship the smallest correct implementation of the agreed design, so glue and app can consume it once tagged.

### What I did

Wrote the tests first, red, then the implementation. In `/httph.go`: added `ScriptSrcNonce` and `StyleSrcNonce` to `httph.ContentSecurityPolicyOptions` after the directive fields, an unexported `contextKey` type with `nonceContextKey`, and `httph.GetNonceFromContext`. Inside the `httph.ContentSecurityPolicy` handler, right after `optsFunc(opts)`, one `rand.Text()` nonce is generated when either bool is set, put in the request context, and appended to `opts.ScriptSrc` and/or `opts.StyleSrc` through a small `appendNonce` helper that handles the empty-value case with no leading space. The next handler gets `r.WithContext(ctx)`. Bumped `/go.mod` to `go 1.24` and ran `go mod tidy` (no dependency changes).

In `/httph_test.go`: seven new subtests in `TestContentSecurityPolicy` covering script-only, style-only, both directives sharing one nonce, the untouched default header, per-request freshness, nonce length, and the empty-directive case, plus a `TestGetNonceFromContext` for the no-nonce context. A `serveWithCSP` test helper runs the middleware and returns the header value together with the nonce the inner handler observed, which keeps each subtest to an assertion or two.

### Why

Appending is done on the options struct before the header is assembled, so the nonce flows through the existing `maybeAddDirective` path and there is no second place that knows how directives are formatted. The options struct is built fresh per request inside the handler, so mutating it carries no cross-request risk.

### What worked

TDD was cheap here: the test helper made the eight cases mostly one-liners, and the first implementation passed them all. `make test` reports 95.0% coverage, `make lint` reports 0 issues.

### What didn't work

Nothing failed beyond the intended red phase, which was the expected `opts.ScriptSrcNonce undefined (type *httph.ContentSecurityPolicyOptions has no field or method ScriptSrcNonce)` and `undefined: httph.GetNonceFromContext`.

### What I learned

CI needs no change: `/.github/workflows/ci.yml` uses `go-version-file: go.mod`, so the 1.24 bump propagates on its own.

### What was tricky

Nothing deep during the build. The self-review afterwards was where the real work was, see below.

### Self-review

Two competing review agents read the diff. What both of them found, and what I did about it:

- The "generates a different nonce for each request" test built a *new* middleware chain per request through the `serveWithCSP` helper, so it compared two independent handler instances and would have passed even if the nonce were generated once per `httph.ContentSecurityPolicy` call. This is the classic bug in nonce middleware and the test aimed at it did not cover it. Rewritten to drive two requests through one handler, and it now also asserts both headers, so a nonce accumulating in `opts.ScriptSrc` across requests would fail too. The implementation was in fact correct, because the options struct is allocated inside the per-request closure, but nothing pinned that down.
- `next.ServeHTTP(w, r.WithContext(ctx))` ran on every request, and `http.Request.WithContext` shallow-copies the request, so every existing user paid an allocation for a feature they had not enabled. The request is now only cloned inside the nonce branch.
- A non-empty `ScriptSrcElem` overrides `script-src` for script elements, so a nonce in `script-src` is silently inert for them, and the same for `StyleSrcElem`. Nonces on `*-elem` are out of scope for this change, so both option fields now document the interaction, and a test locks in that the nonce is not added to those directives.
- The doc said "appends", but on an empty directive the middleware *creates* the directive, which turns off the `default-src` fallback for it. Both field comments now say so.
- Nothing said that a nonced response must not be stored by a shared cache. Added to the `httph.ContentSecurityPolicy` doc.
- `const nonceContextKey contextKey = iota` outside a grouped `const` block just means 0, and reads as "first of a series"; a second key declared the same way later would silently collide. Now a `contextKey` string with the value `"nonce"`, which also reads better in a context dump.
- The nonce test asserted `len(nonce) >= 26`, which only re-tests `rand.Text`'s documented behaviour. It now also asserts the nonce matches the CSP base64-value charset, so a future generator change cannot inject a space or a `;` into the header.
- Smaller ones: the struct doc claimed every field name is a directive, which the two bools are not; `serveWithCSP` returned two bare strings; and there was no empty-`StyleSrc` case to mirror the `ScriptSrc` one. All fixed.

Both reviewers also flagged two things I deliberately left alone. The `go 1.19` to `go 1.24` bump is a hard floor for every importer, and they suggested hand-rolling the nonce from `rand.Read` to avoid it, but that trade-off was made in Step 1 and is not mine to reverse. And both preferred `NonceFromContext` over `GetNonceFromContext`, per the stdlib's `httptrace.ContextClientTrace` shape; the `Get` prefix is a deliberate match for glue's `GetUserIDFromContext`, also decided in Step 1.

### What warrants review

The `*-elem` interaction is documented, not handled. If apps set `ScriptSrcElem` in practice, a `ScriptSrcElemNonce` follow-up is the obvious next step. Also worth a look: whether the nonce fields read better next to their directives in the struct than grouped at the end.

### Future work

glue#203 and app#64, once this is tagged. Possibly `ScriptSrcElemNonce`/`StyleSrcElemNonce`, if the `*-elem` override bites anyone.
